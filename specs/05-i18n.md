# 05 — i18n FR / EN / JA

## État : terminé
Trois langues servies de bout en bout, UI **et** contenu CMS.

- CMS : Polylang + `wp-graphql-polylang`. FR par défaut, EN et JA traduites
  (`wp/i18n-setup.php`, `wp/i18n-cpt.php`, `wp/i18n-translate.php`).
  Slugs Polylang : `osaka-2025`, `osaka-2025-en`, `osaka-2025-ja`.
- Front : routes `src/app/[lang]/…`, `src/middleware.ts` redirige tout chemin nu vers `/fr`.
- `<html lang>`, `openGraph.locale`, `inLanguage` (JSON-LD) et dates `Intl` suivent la langue.
- `canonical` + `hreflang` fr/en/ja/x-default sur chaque page ; les fiches pointent
  vers le slug de chaque langue (`slugAlternates`).
- Sitemap : 3 × (8 pages statiques + éditions + actus), avec `alternates.languages`.
- Image OG générée par langue (`src/app/[lang]/opengraph-image.tsx`).
- Formulaire de contact : libellés, placeholders et messages de validation traduits,
  côté client **et** côté serveur (`/api/contact` lit le champ `lang`).
- Webhook `/api/revalidate` purge les pages des trois langues.

## Où vivent les textes
| Quoi | Où |
|---|---|
| Libellés d'interface, métadonnées, FAQ, contenus vitrine | `frontend/src/i18n/dict.ts` (`fr` / `en` / `ja`) |
| Helpers langue (préfixes, slugs, hreflang, code WPGraphQL) | `frontend/src/i18n/lang.ts` — **module serveur, pas de `'use client'`** |
| Hook client de langue courante | `frontend/src/i18n/useLang.ts` |
| Redirection des chemins sans langue | `frontend/src/middleware.ts` |
| Éditions, actus, médias | CMS, requêtés avec `language: wpLanguage(lang)` |

## Règles à respecter
1. `src/i18n/lang.ts` ne doit **jamais** redevenir un module client : `generateStaticParams`
   y lit `LANGS`, un `'use client'` casse le build (`Attempted to call map() from the server`).
2. Tout lien interne passe par `lz(path, lang)` / `localizePath` — sinon le middleware
   renvoie l'internaute sur `/fr` et la navigation perd la langue.
3. Toute requête CMS passe `language: wpLanguage(lang)`. Pas de `'FR'` en dur.
4. Les données vitrine indexées par slug (`EDITION_DETAILS`, `EDITION_CREDITS`,
   `t.editionDetails`, `t.eventTypes`) sont **clés sur le slug FR** : utiliser `baseSlug(slug)`.
5. Nouvelle clé de dictionnaire : l'ajouter dans `fr`, puis surcharger dans `en` et `ja`
   (`en`/`ja` étalent `fr`, une clé non surchargée reste donc en français).
6. Le middleware doit rester dans **`src/middleware.ts`**. Le projet utilisant un dossier
   `src/`, un `middleware.ts` à la racine de `frontend/` est ignoré silencieusement :
   ni erreur ni avertissement, mais `/` renvoie 404 et toutes les redirections legacy
   de `next.config.js` (qui pointent vers des chemins sans langue) tombent avec. Contrôle :
   la ligne `ƒ Middleware` doit apparaître dans la sortie de `npm run build`.

## Limite connue
`notFound()` appelé dans une page (slug inconnu) renvoie bien un **404 HTTP**, mais Next 14
rend la coquille `__next_error__` et hydrate le contenu côté client : le layout racine
ne fournit pas `<html>`/`<body>`, puisque l'attribut `lang` dépend du segment `[lang]`.
Lui rendre `<html>` au niveau racine imposerait `headers()` et ferait perdre le
pré-rendu statique de tout le site. Les URL non routées (`/en/zzz`) passent, elles,
par `src/app/not-found.tsx` qui fournit un document complet et se rend côté serveur.
